# 분석 시간축(단기·중기·장기)을 1급 개념으로 만들기 — 계획 (2026-08-30)

`Report/case_b_swot_vs_paper.md`의 후속. SWOT에서 나온 결론을 **"우리 도구는 단기
분석에 집중돼 있다"** 는 프레임으로 다시 정리하고, 그 약점을 고치되 **강점은 유지·강화**
하는 것이 목표다.

아래 코드 인용은 전부 직접 확인한 것이다.

---

## 1. 문제의 정확한 형태 — 버그가 아니라 **설계 공백**이다

SWOT에서는 이걸 "head bias 버그"로 불렀지만, 더 정확한 진단은 이것이다:

> **우리 파이프라인에는 "이 분석이 어느 시간 범위를 다루는가"라는 개념 자체가 없다.**

증거 — AI에게 전달되는 것 중 **시간 범위를 알려주는 항목이 하나도 없다**:

- `src/pipeline.js`의 `sourceProfiles`: `sourceFile`, `formatId`, `formatLabel`,
  `entityColumn`, `rowCount`, `derivedAlarmCount` — **시간 범위 없음**
- `src/figures.js:325`의 `figureCatalog()`: `id`, `claim`, `available`,
  `unavailableReason`, `evidenceTier`, `summaryStats` — **시간 범위 없음**
- `src/log-engine.js`는 `timestampColumn`을 감지해 두고도(310행) 그 열의
  **관측 최소·최대 시각을 어디에도 보관하지 않는다**

그 결과 계층별로 시간 커버리지가 제각각인데 아무도 그 사실을 모른다:

| 계층 | 실제 커버리지 | 근거 |
|---|---|---|
| 시계열/그림 (B-F3 등) | **전 구간** | `series-engine.js`의 adaptive/day rebinning이 전 구간을 2000 bin으로 압축 |
| 저항 이벤트 (B-F1/B-F4) | 초기 기준선 + 최근 창 | PR #4에서 수정됨 |
| **알람 컨텍스트** | **가장 이른 40건뿐** | `log-engine.js:288` `if (bucket.alarmSamples.length < ALARM_SAMPLE_CAP)` |
| 파생 집계 (`categoryCounts`) | 전 구간 합계 (시간축 없음) | `log-engine.js:203` |

**AI가 결론의 뼈대로 삼는 것은 알람 컨텍스트다.** 그래서 Case B 보고서의 헤드라인이
1,353일 중 165~217일 구간(12~16%)에 갇혔다. 그런데 모델은 자기가 좁은 창만 봤다는
사실조차 알 수 없었다 — 아무도 알려주지 않았으니까.

## 2. 시간축 정의 (이 데이터 기준)

| 구분 | 범위 | 무엇을 보는가 | 현재 상태 |
|---|---|---|---|
| **단기** | 수 시간 ~ 수 주 | 과도 이벤트, IR 서명, 전류 방향 추종 편차, 알람 전후 맥락 | ✅ **강점** — Case B에서 `\|Vdev\|/\|I\|` 0.23~0.29mΩ 수렴 같은 기전 수준 판별을 실제로 해냄 |
| **중기** | 수 주 ~ 수 개월 | 계절/분기 추세, 편차 확대 여부 | ⚠️ 부분 — 일 단위 시계열은 있으나 추론 계층에 전달 안 됨 |
| **장기** | 수 개월 ~ 수 년 | 열화 궤적, knee, 셀 지목의 시간적 변화 | ❌ **공백** — 논문의 500일·3년 주장을 검증할 수단 없음 |

**단기 강점을 줄이지 않는다.** 단기 분석은 이 도구가 GP 기반 논문보다 실제로 잘하는
부분이다(SWOT S2). 문제는 단기 결론이 **전 구간을 대표하는 것처럼 제시된다**는 것이지,
단기 분석 자체가 아니다.

## 3. 작업

### T1 — 시간 커버리지를 측정하고 AI·엔지니어 양쪽에 알린다 (최우선)

**이걸 먼저 해야 하는 이유**: T2에서 샘플링을 아무리 개선해도, 모델이 "내 근거가 어느
구간에서 왔는지" 모르면 여전히 좁은 창의 결론을 전 구간 결론처럼 쓴다. 커버리지를
드러내는 것이 샘플링을 고치는 것보다 **선행**한다.

- 스트리밍 중 `timestampColumn` 기준 **관측 최소/최대 시각**을 버킷에 보관
  (고정 크기 2개 값이므로 메모리 부담 없음).
- `sourceProfiles`에 데이터 전체 범위를, 그리고 **알람 컨텍스트가 실제로 덮는 범위**를
  각각 담는다. 이 둘은 다른 값이며 **반드시 구분**할 것.
- 둘이 크게 어긋나면(예: 근거 구간이 전체의 20% 미만) 기존 `buildTruncationNote`와
  같은 비은닉 패턴으로 프롬프트와 UI 양쪽에 명시한다. 이 저장소의 원칙("생략은 절대
  침묵하지 않는다")을 시간축에도 적용하는 것이다.
- `figureCatalog()`에도 각 그림이 덮는 시간 범위를 넣는다 — 지금은 그림이 전 구간을
  덮는데도 모델이 그 사실을 모른다.

### T2 — 알람 샘플을 전 구간에 걸쳐 뽑는다

`src/log-engine.js:288`의 "앞에서 40건" 정책을 **시간 계층화(stratified) 유지**로 교체.

- PR #4의 `considerResistanceEvent` 수정과 같은 계열의 문제이므로, 그 패턴
  (초기 기준선 보존 + 최신 창 순환 + drop 카운트 비은닉)을 참고하되, 여기서는
  **전 구간에 고르게 퍼지는 것**이 목적이므로 그대로 복사하지 말고 적합한 방식을
  선택할 것(예: 시간 버킷별 할당, reservoir sampling).
- 버려진 알람 건수와 **유지된 샘플의 시간 분포**를 노출할 것. 단순 개수보다 분포가
  중요하다.
- **단기 맥락의 질을 떨어뜨리지 말 것**: 각 알람 샘플은 지금처럼 `CONTEXT_WINDOW`
  전후 맥락을 유지해야 한다. 개수를 늘리려고 맥락을 얇게 만들면 S2 강점이 죽는다.

### T3 — 파생 집계에 시간축을 넣는다

지금 `derived.categoryCounts.outlierCell`은 전 구간 하나의 합계다("Cell 8 99%").
이걸 **시간 버킷별로도** 집계하면 "2018년엔 Cell 8, 2021년엔 다른 셀" 같은 변화가
비로소 보인다.

- 버킷 개수는 고정 상한을 둘 것(무한 증가 금지 — 이 저장소의 기존 규율).
- 이것이 논문의 "500일 이후 상승", "3년 knee" 주장을 **우리 데이터로 직접 테스트**할 수
  있게 만드는 핵심이다. 다만 **논문 수치를 threshold로 하드코딩하지 말 것**
  (전략 문서가 명시적으로 금지).

### T4 — 보고서가 자기 시간축을 밝히게 한다

- `buildDraftReportPrompt`에 근거 시간 범위와 커버리지 비율을 전달.
- 근거가 특정 구간에 몰려 있으면 헤드라인/근본원인 서술이 **그 사실을 명시**하도록
  프롬프트에 규칙 추가. 예: 전 구간의 일부만 본 경우 전 구간 특성으로 단정 금지.
- **결론을 지시하지 말 것.** 커버리지를 사실로 전달하고, 판단은 기존대로 근거 기반
  서술과 사람 검토에 맡긴다.
- 장기 근거가 없으면 `unknownBox`에 "장기 거동 미확인"이 들어가야 한다 — 없는 것을
  있는 것처럼 쓰지 않는 기존 원칙 그대로.

## 4. 하지 말 것

- **GP/BattGP 급조 구현.** B-F5는 계속 `unavailable`로 둔다. 품질이 담보되지 않은 GP는
  이 프로젝트의 주장-한계 원칙을 무너뜨린다.
- **논문 수치(500일/800일/3년)를 threshold나 기대값으로 코드에 심는 것.**
- **단기 분석 축소.** 강점이다. 시간축 라벨을 붙이는 것이지 줄이는 게 아니다.
- **장기 결론 자동 생성.** 근거가 얇으면 `unknownBox`로 남기는 것이 정답이다.
- 프롬프트 예산 상수 재조정(이미 충분히 작다고 실측으로 확인됨).
- Web Worker 도입.

## 5. 검증 기준

- `npm run test:unit`, `npm run build` 통과.
- **유닛 테스트**: 시간 커버리지 계산(전 구간 vs 근거 구간), 계층화 샘플링이 실제로
  전 구간에 퍼지는지(초기 편중이 사라졌는지), 커버리지 부족 시 고지가 나오는지.
- **종단 검증 (필수)**: `Log_sample/extracted/data_sys_6_stride80.csv`로 실제 앱을
  돌려서 다음을 확인하고 스크린샷을 남길 것:
  1. 알람 근거가 2018년 말에만 몰리지 않고 **2019~2021년 구간도 포함**되는지
  2. UI와 프롬프트에 시간 커버리지가 표시되는지
  3. `outlierCell` 지목이 시간에 따라 변하는지 아닌지 — **변한다면 그 자체가 중요한
     발견**이고, 안 변한다면 Cell 8 지목이 전 구간에서 견고하다는 뜻이다. **어느
     쪽이든 사실대로 기록할 것.**
- 결과는 `Report/analysis-horizons-findings.md`에. 못 한 것과 그 이유도 쓸 것.
