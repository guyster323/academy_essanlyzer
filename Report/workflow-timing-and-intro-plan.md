## 2. 작업 A — 워크플로우 실측 (먼저 할 것, 나머지의 근거가 된다)

두 경로를 **각각** 측정하고, 단계별 wall-clock을 기록할 것:

1. **샘플 데이터 경로** — 초보자 가이드가 실제로 설명하는 경로(내장 샘플/데모 데이터로
   Step 1→5). 이게 "5분 안에 끝"이 맞는지 틀린지를 정하는 유일한 근거다.
2. **골드 Case B 경로** — `Log_sample/extracted/data_sys_6_stride80.csv` (이 워크트리에
   이미 있음). detect-anomaly 수치는 이미 있으니
   (`Report/latency-effort-real-outputs/COMPARISON.md`), 없는 것은
   **generate-hypotheses / draft-report**다. 이전 세션에서 429로 못 쟀다.

기록할 것: 단계별 소요 시간, 총 소요 시간, 측정 일시, 사용한 입력. 실패·429도 그대로
기록할 것.

**429(지출 한도)를 만나면**: 무리해서 우회하지 말 것. 몇 번 시도했고 언제 막혔는지
기록하고, 그때까지 얻은 부분 측정치라도 남길 것. `Report/case_b_findings.md`에 있는
과거 실측치(가설 생성 5~13분, 보고서 생성 9~10분)를 **"과거 관측치, 이번에 재측정
못 함"** 으로 명시해 쓰는 것도 정당하다 — 다만 새로 잰 것처럼 쓰지 말 것.

## 4. 작업 C — 데모 재촬영 (ffmpeg)

**ffmpeg 위치**: `C:\Program Files\Metadata++\ffmpeg.exe` — **PATH에 없다.** 전체 경로로
호출할 것. gyan.dev full build이고 `libx264`, `gif`, `libwebp`, `gdigrab` 전부 있다
(확인 완료).

### 촬영 방식 — 두 가지 중 선택 (권장: Playwright)

**(권장) Playwright `recordVideo`**: 이 저장소는 이미 Playwright를 쓴다
(`tests/e2e/`, `playwright.config.js`). 결정적이고 재현 가능하며, 화면 해상도/커서/
다른 창이 끼어들지 않는다. `.webm`이 나오면 ffmpeg로 mp4/gif 변환.

**(대안) ffmpeg `gdigrab`**으로 실제 Chrome 창 캡처. 실제 브라우저 그대로라는 장점이
있지만, 창 위치·다른 창 간섭·커서 등 변수가 많다. 이번 세션에서 창 ID가 몇 초 만에
stale해지는 문제를 이미 겪었다(`Report/case_b_findings.md`).

### ⚠️ 반드시 지킬 편집 원칙 — 시간 압축을 숨기지 말 것

30분 넘는 과정을 40초 영상으로 만드는 것 자체는 정상적인 편집이다. **하지만 그걸
숨기면 안 된다.** 지금 README는 "전체 데모 영상 보기 (MP4, 38초) — 업로드→이상탐지→
가설→사람 검토→보고서까지 전 과정 실행"이라고만 적혀 있어서, **읽는 사람은 전 과정이
38초에 끝난다고 오해하게 된다.** 이건 이 프로젝트가 스스로 지키는 원칙("근거 없는
주장 금지", "생략은 침묵하지 않는다")을 문서가 어기고 있는 셈이다.

따라서:
- 영상/GIF 안에 **또는** 바로 옆 캡션에 "실제 소요 N분, 대기 구간 압축" 같은 표기를
  **반드시** 넣을 것.
- 대기 구간을 잘라냈으면 잘라냈다고 쓸 것.
- 실제보다 빨라 보이게 만드는 어떤 연출도, 그 사실을 표기하지 않은 채로는 금지.

## 6. 타임아웃 관련 주의 (사용자가 특별히 짚은 부분)

이 작업은 **오래 걸리는 것이 정상**이다. 다음을 미리 조정하지 않으면 측정·촬영이
중간에 죽는다:

- **`playwright.config.js`의 `timeout: 30 * 1000`** — 테스트당 30초다. 실제 워크플로우
  한 단계가 700초 이상이므로 **그대로 두면 100% 실패한다.** 측정/촬영용 스펙에는
  `test.setTimeout()`으로 넉넉히(단계당 30분 이상, 전체 90분 이상) 잡을 것.
  **기존 e2e 테스트의 30초 기본값은 건드리지 말 것** — 그건 빠르게 실패해야 하는
  테스트다. 측정용 스펙에서만 개별적으로 올릴 것.
- **`webServer.timeout: 30 * 1000`** — Vite 기동용이라 그대로 둬도 된다.
- **`CLAUDE_CLI_TIMEOUT_MS`** — 코드 기본값이 이미 30분(`1_800_000`)이다. 낮추지 말 것.
- **워커 자신의 명령 타임아웃** — 한 단계가 20분 넘게 걸리므로, 단계를 기다리는 명령은
  백그라운드로 돌리고 폴링하는 방식이 안전하다. 포그라운드로 20분짜리 명령을 걸면
  도구 타임아웃에 걸린다.
- 포트 충돌: 형제 체크아웃이 5173을 쓸 수 있다. `PW_PORT`로 이 워크트리 전용 포트를
  지정할 것 (`playwright.config.js`가 이미 지원한다).

## 7. 우선순위

**A(실측) → B(문서 정정) → D(인트로) → C(재촬영)** 순서를 권장한다. A·B·D는 확실한
가치가 있고 비교적 빠르다. C(재촬영)는 가장 오래 걸리고 실패 변수가 많으므로 마지막에
둔다.

**429나 촬영 실패로 C를 못 끝내면, A·B·D만 확실히 끝내고 C는 남길 것.** 잘못된 수치를
그대로 둔 채 영상만 새로 찍는 것보다, 수치를 바로잡고 영상은 다음으로 미루는 편이
훨씬 낫다. 못 한 것은 findings에 그대로 쓸 것.
