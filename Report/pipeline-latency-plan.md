# 파이프라인 지연시간(latency) 축소 계획 (2026-08-30)

> **이후 정정됨 / superseded (2026-08-30).** 이 문서의 1순위 가설 — `anomalyWindows`에
> `maxItems`가 없어서 출력 길이가 들쭉날쭉하고, 그게 700초 지연의 원인이라는 것 — 은
> `Report/latency-root-cause-and-plan.md`의 실측으로 뒤집혔다. 약 200자 프롬프트만으로도
> 220–367초가 걸렸고, 5회 모두 이상 구간은 12–16건만 나왔다. 상한이 없어서 40건씩
> 쏟아낸 게 아니었다. `maxItems`는 **일관성 문제로는 여전히 유효**하지만 **지연시간
> 해결책이 아니다.** 이 문서는 당시의 코드-읽기 가설 기록으로 보존한다. 실행 근거는
> `latency-root-cause-and-plan.md` / `latency-findings.md`를 따른다.

`Report/rank-3-4-findings.md`(Rank 3: CLI 고정 오버헤드 제거)의 후속. Rank 3에서 이미
확인됐듯, `--safe-mode` 등은 **매 호출마다 붙는 고정 기동비용**만 없앨 뿐 실제 모델
사고 시간은 줄이지 못한다 (같은 stride80 detect-anomaly 프롬프트가 플래그 적용 후에도
700.9초). 이 문서는 "그 700초 자체를 줄이려면 무엇을 할 수 있는가"를 다룬다.

**아직 아무 코드도 바꾸지 않았다** — 사용자가 "계획문서부터" 보길 원해서, 근거 확인만
마치고 실행은 보류한 상태.

---

## 실측/코드로 이미 확인된 것

- Rank 3 실측: 플래그 적용 후에도 `duration_api_ms`가 wall-clock의 거의 전부 —
  즉 CLI 오버헤드가 아니라 **순수 모델 처리 시간**이 병목이다.
- 같은 입력(stride80)인데도 detect-anomaly가 어떤 실행에서는 700.9초, 다른 실행에서는
  약 2.5분으로 **편차가 컸다** (`Report/rank-3-4-findings.md`의 재발행 로그 대조). 입력
  프롬프트 크기는 이미 작고 안정적이라는 걸 증명해뒀으니(Rank 3 문서), 이 편차는 입력이
  아니라 **출력 쪽 변동**으로 설명하는 게 더 그럴듯하다 — 그리고 실제로 그 이유를
  코드에서 찾았다.
- `server/lib/schemas.js`의 `report_anomaly_detection` 스키마: `anomalyWindows` 배열에
  **`maxItems`가 없다**. 이 파일의 다른 모든 배열(`detected_issues`의 issues: maxItems 4,
  `hypotheses`: maxItems 3, `ftaLeaves`: maxItems 12, `evidenceCitations`: maxItems 20,
  `managementImplications`: maxItems 5)은 전부 상한이 있는데 이것만 없다. 항목당 9개
  필수 필드(timestamp/sourceFile/parameter/observedValue/normalRange/deviation/
  alarmCode/level/evidenceTier)를 요구하므로, 모델이 이번엔 "이상 구간 40개"를 쓰기로
  했다면 다음번 "이상 구간 8개"보다 훨씬 오래 걸리는 게 당연하다 — **입력이 아니라
  출력 길이가 실행마다 들쭉날쭉했을 가능성이 가장 유력한 원인.**
- `hypotheses`(최대 3개 × 13개 필수 필드, 각각 evidence/disconfirmingEvidence/
  missingSignals 등 실제 사고가 필요한 서술형 필드)와 `report_draft`(핵심 8개 서술형
  필드 + FTA 최대 12개 + citation 최대 20개 + management 최대 5개 + 이메일 본문 전체)는
  원래부터 출력량이 많다 — 가설생성 13분, 보고서생성 10분이 detect-anomaly보다 길게
  나온 것과 방향이 일치한다. 이건 버그가 아니라 **이 프로젝트가 의도적으로 요구하는
  근거 등급/반증 근거/FTA 엄밀함의 비용**이다.
- `buildHypothesesPrompt`/`buildDraftReportPrompt`는 원본 로그 텍스트(`combinedLogText`)
  를 다시 보내지 않는다 — 이전 단계의 구조화된 JSON 결과만 넘긴다. 즉 뒤 단계들이
  느린 게 "원본 로그를 계속 다시 보내서"는 아니다. (지난 턴에 캐싱을 1순위로 제안했던
  건 이 부분을 확인하기 전이라 근거가 약했다 — 아래에서 우선순위를 내렸다.)

## 제안 (확신도 순)

### 1. `anomalyWindows`에 `maxItems` 상한 추가 — 가장 확실하고 위험이 적음

이 프로젝트의 기존 패턴(다른 배열은 전부 상한 있음, 잘린 건 침묵하지 않고 명시)과
동일하게 맞추는 것뿐이다. 상한을 넘는 이상 구간이 실제로 있다면 "N건 중 상위 K건만
표시, 나머지는 추가 확인 필요"처럼 **명시적으로** 표시해야 한다 (`buildTruncationNote`
patttern 재사용). 상한 값 자체는 실제 Case A/B 골드런에서 사람이 검토 가능한 개수가
몇 개였는지 확인 후 정해야 한다(예: UI에서 실제로 몇 개까지 스크롤해서 보는지, 사람이
5단계 리뷰에서 몇 개나 참고했는지) — 근거 없이 숫자만 넣지 않는다.

**검증 기준**: 같은 입력을 여러 번 돌려서 detect-anomaly wall-clock의 표준편차가 실제로
줄어드는지 확인. 상한에 걸리는 실제 케이스가 있는지도 같이 기록.

### 2. `--effort` 튜닝 실측 — 싸고 빠르게 해볼 수 있는 실험

지금 `server/lib/claude-cli.js`는 effort를 전혀 지정하지 않는다(CLI 기본값 사용).
`--effort medium`(또는 low)로 hypotheses/draft-report 호출을 실측해서:
- wall-clock이 실제로 줄어드는지
- 줄어든다면, evidenceTier/disconfirmingEvidence/missingSignals/claimLimit 같은 근거
  엄밀성 필드의 **내용 품질**이 유지되는지 (자동으로 판단하기 어려우니, 최소한 같은
  입력에 대해 high/xhigh 결과와 medium/low 결과를 나란히 놓고 사람이 비교)

품질이 떨어지면 이 프로젝트의 핵심 가치(과잉 확신 방지)와 정면으로 충돌하니 채택하지
않는다. **속도만 보고 판단하지 말 것.**

### 3. 체감 대기시간 개선 — 실제 시간은 안 줄지만 리스크 없음

`claude` CLI는 `--output-format stream-json`을 지원한다(현재는 `json`으로 블로킹
호출). 스트리밍으로 바꾸면 로딩 화면에 "경과 N초" 카운터 대신 모델이 생성 중인 부분
텍스트를 실시간으로 보여줄 수 있다. 실제 wall-clock을 줄이는 게 아니라 "멈춘 것처럼
보이지 않게" 하는 것 — 별도 트랙으로 낮은 리스크에 진행 가능하지만, 서버(SSE 등)와
클라이언트 로딩 화면 둘 다 손대야 하는 작업이라 규모가 작지 않다.

### 4. 단계 간 프롬프트 캐싱 — 우선순위 하향

지난 턴에 1순위로 제안했지만, 위에서 확인했듯 hypothesis/report 단계는 원본 로그를
재전송하지 않아 단계 간 공유되는 대용량 텍스트가 애초에 많지 않다. 캐싱이 진짜 도움될
곳은 "같은 입력으로 504 이후 재시도하는 경우"인데, 이건 Anthropic API의 프롬프트
캐시가 세션과 무관하게 프롬프트 내용/직전 캐시 기준으로 동작한다는 걸 이미 이번
세션에서 직접 확인했으므로(완전히 다른 두 CLI 프로세스 호출 사이에서도 캐시 read가
일어남), **재시도는 코드를 안 건드려도 이미 어느 정도 자동으로 혜택을 볼 가능성이
있다** — 새 기능을 만들기 전에, 실제 504 재시도 상황에서 `cache_read_input_tokens`가
찍히는지부터 확인하는 게 먼저다. 확인 후에도 의미 있는 이득이 없으면 이 항목은
접는다.

### 5. `AI_PROVIDER=api`로 전환 — 엔지니어링이 아니라 비즈니스 결정

CLI 기동 오버헤드를 완전히 없앨 수 있지만 종량제 과금이 생긴다. "구독 재사용, 별도
과금 없음"이라는 이 프로젝트의 데모 설계 원칙과 정면으로 충돌하므로, 이건 코드
변경이 아니라 사용자가 직접 판단할 문제로 남겨둔다. 이 계획의 실행 범위에 포함하지
않는다.

## 명시적으로 하지 않는 것 (제품 판단 없이는 손대지 않음)

- 가설 개수(최대 3→더 적게)나 이메일 본문·FTA 항목 수를 줄여서 출력량 자체를 줄이는
  것 — 속도는 늘겠지만 이 프로젝트가 의도적으로 요구하는 근거 엄밀성을 깎는 일이라
  사용자의 명시적 판단 없이는 진행하지 않는다.
- 프롬프트 예산 상수(`MAX_TOTAL_ALARM_CONTEXTS` 등, Rank 3에서 이미 충분히 작다고
  확인됨) 재조정.
- 사람 검토 체크포인트(5단계 중 사람이 가설·심각도를 확정하는 지점) 생략/자동화.
