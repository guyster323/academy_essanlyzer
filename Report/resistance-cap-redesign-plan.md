## 1. 문제의 정확한 형태 — 시뮬레이션으로 확인함

현재 `src/forensics/lfp.js`의 `appendCappedResistanceEvent`는 PR #4에서 도입한
**"초기 기준선 2000 + 최근 창 2000"** 구조다:

- `[0, 2000)` — 처음 본 2,000건을 **영구 고정**
- `[2000, 4000)` — 최근 2,000건 순환 버퍼

이건 PR #4가 고친 "최신 이벤트를 조용히 버리는 버그"에 대한 올바른 처방이었다.
**그러나 이벤트 밀도가 높아지면 그 자체가 병리적으로 변한다.**

Case B 원본 해상도와 같은 형태(579,026건, 2018-04-28~2022-01-10)를 실제로 넣어 본 결과:

```
kept: 4000 | dropped: 575026
retained by year: {"2018": 2000, "2022": 2000}
first: 2018-04-28 | last: 2022-01-10
largest gap inside retained sample: 1344 days (2018-05-02 -> 2022-01-05)
```

**2019·2020·2021년이 0건이다.** 남는 건 가동 첫 **나흘치**(2018-04-28~05-02) 2,000건과
마지막 2,000건뿐이고, 그 사이 **1,344일이 완전히 비어 있다.**

### 이것이 실제로 무엇을 망가뜨렸는가 (PR #9 실측)

| 증상 | 실측값 | 이 구조로 설명되는가 |
|---|---|---|
| `matchedCount` 급감 | 1,330(stride80) → **603**(원본) | ✅ 운영점(SOC/T/I) 매칭이 1,344일 떨어진 두 덩어리 사이에서 성립하기 어렵다 |
| B-F4 knee 탐지 불가 | `저항 시계열이 짧아 knee를 독립 탐지할 수 없음` | ✅ 시계열이 아니라 **시간축 양 끝의 점 두 덩어리**다 |
| 셀 지목 불안정 | stride80 Cell 5 → 원본 Cell 1 | ✅ `outlierCellByResistance`는 유지분의 앞 1/5 vs 뒤 1/5 중앙값 차이인데, 표본이 3.7년 떨어진 이봉(bimodal) 분포다 |

**그리고 가장 중요한 것**: 파생 이상 밀도가 30~60배로 폭증하는 **2021년**
(`Report/analysis-horizons-stride80.json`, 논문의 3년 knee 시점)이 저항 증거에서
**통째로 빠져 있다.** 정작 봐야 할 구간이 없다.

즉 지금 상태에서 B-F1/B-F4는 **어느 해상도로도 셀을 판정할 근거가 못 된다.**

## 2. 방향 — 이미 검증된 수정 패턴이 있다

PR #8에서 `alarmSamples`에 똑같은 종류의 문제(앞쪽 40건만 유지)를 고쳤고, **시간 계층화
(stratified) 유지**로 분포가 `40,0,0,0,0,0,0,0` → `1,6,7,6,7,3,5,5`로 개선됐다.
저항 이벤트도 같은 방향이다: **전 구간에 고르게 퍼지게 할 것.**

다만 **그대로 복사하지 말 것.** 저항 이벤트에는 알람 샘플에 없는 제약이 있다:

- **스트리밍 중에는 전체 구간을 모른다.** 마지막 타임스탬프를 미리 알 수 없으므로
  "구간을 N등분해 배분"을 처음부터 확정할 수 없다. 구간이 늘어남에 따라 재배분하는
  방식(예: 버킷이 차면 해상도를 반으로 접는 방식)이나 시간 가중 reservoir sampling이
  필요하다. `src/series-engine.js`의 `pairwiseMerge`가 정확히 이 문제
  (**미리 범위를 모른 채 고정 개수로 전 구간을 대표하기**)를 이미 풀고 있으니 참고할 것.
- **초기 기준선은 여전히 필요하다.** 열화 판정은 "초기 대비" 비교이므로 가동 초기
  표본을 완전히 잃으면 안 된다. 다만 **나흘치 2,000건은 과하다** — 훨씬 적은 수로 충분하다.
- `outlierCellByResistance`가 "앞 1/5 vs 뒤 1/5"를 쓰므로, 유지 표본의 **시간 순서가
  보존**되어야 한다(현재 `normalizeResistanceEvents`가 하는 역할).

### 반드시 지킬 것

- `MAX_RESISTANCE_EVENTS`(메모리 상한)를 **키우는 것으로 해결하지 말 것.** 같은 4,000건
  예산 안에서 **분포를 고치는 것**이 이번 과제다. 상한을 올려야 한다는 판단이 서면
  **측정 근거를 먼저 제시**하고 findings에 남길 것.
- drop 건수와 **유지 표본의 시간 분포**를 노출할 것. PR #8에서 알람 샘플에 대해 한 것과
  같은 비은닉 처리. 개수보다 분포가 중요하다.
- `LFP_DI_THRESHOLD` 등 이벤트 채택 임계값은 건드리지 말 것 — 이번 과제는 **채택된
  이벤트를 어떻게 보관하느냐**이지 무엇을 이벤트로 볼 것이냐가 아니다.

## 3. 검증 기준

**(a) 유닛 테스트** — 최소한 다음을 고정할 것:
- 579,026건을 3.7년에 걸쳐 넣었을 때 **모든 연도에 표본이 남는지**(현재는 2019~2021이 0)
- 유지 표본 내부의 최대 시간 공백이 전체 구간 대비 합리적인 수준인지
  (현재는 1,344일 / 1,353일 = 99%)
- 초기 기준선이 일정 부분 보존되는지
- 시간 순서가 보존되는지 (`outlierCellByResistance` 전제)
- drop 카운트와 시간 분포가 노출되는지
- 이벤트가 캡보다 적을 때 기존 동작이 그대로인지 (회귀 방지)

**(b) 실제 데이터 재측정** — `Log_sample/case_b_field_data.zip`(이 워크트리에 있음)의
`field_data/data_sys_6.csv`로 원본 해상도 스트리밍을 다시 돌려 PR #9 값과 대조:

| 항목 | PR #9 (현 구조) | 재설계 후 |
|---|---|---|
| `matchedCount` / `eventCount` | 603 / 4,000 | ? |
| B-F1 `outlierCell` | Cell 1 | ? |
| B-F4 knee | unavailable | ? |
| 유지 표본 연도 분포 | 2018:2000, 2022:2000 | ? |

**결과를 미리 정하지 말 것.** matched가 늘어날 것으로 기대되지만, 셀 지목이 또 바뀔
수도 있고 여전히 불안정할 수도 있다. **셋 다 정당한 결과**이며 사실대로 기록할 것.
특히 **셀 지목이 안정화됐다고 성급히 결론짓지 말 것** — 한 번의 실행으로는 안정성을
말할 수 없다.

**(c) stride80 회귀 확인** — 기존 stride80 입력에서 행 수(240,603)와 파생 이상(9,366)이
그대로인지. 저항 쪽 값은 바뀌는 것이 정상이다.

`npm run test:unit`, `npm run build` 통과 필수.
